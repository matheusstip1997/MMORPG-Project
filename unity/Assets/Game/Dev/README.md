# Prediction dev scene (backlog D1)

`PredictionDev.unity` connects to a locally running GameServer, predicts your character with reconciliation,
interpolates every other entity, and draws them with the M1 placeholder art (see Visuals below) under the 45-degree camera.

Controls: **WASD** move (screen-relative), **mouse** facing, **C / V** turn the camera (placeholder keys, R-2.2-05).
The HUD (backlog I, `unity/Assets/Game/UI/README.md`) shows your HP, MP and stamina, the hotbar, charges, statuses, name plates,
damage numbers and monster telegraphs. A dev status line at the bottom right shows the server tick, input ack, pending
inputs, corrections and the last error.

## Run it

1. In PowerShell at the repository root, make a dev ticket secret and start the server with it (the server takes base64,
   `DevConnect issue` takes hex; both are the same 32 bytes):

   ```powershell
   $bytes = [byte[]]::new(32); [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
   $env:MMORPG_TICKET_SECRET = [Convert]::ToBase64String($bytes)
   $env:MMORPG_DEV_TICKET_SECRET = ($bytes | ForEach-Object { $_.ToString('x2') }) -join ''
   $env:MMORPG_TICKET_KEY_ID = "1"; $env:MMORPG_REALM_ID = "1"; $env:MMORPG_GAME_PORT = "7777"
   $server = Start-Process dotnet -ArgumentList 'run --project src/GameServer' -NoNewWindow -PassThru
   ```

2. Right before pressing Play (tickets are single use and expire after `NetSecurity.TicketLifetimeMs`, 60 s), in the
   same PowerShell window:

   ```powershell
   dotnet run --project src/Tools/DevConnect -- issue --port 7777
   ```

   It writes `unity/UserSettings/DevTicket.json` (git-ignored). Issue a new one for every Play.

3. Open `Assets/Game/Dev/PredictionDev.unity` and press Play. Stop the server with `Stop-Process $server.Id`
   (or Ctrl+C in its window).

To feel the reconciliation, add latency or loss with a tool such as clumsy (Windows) on UDP port 7777: the capsule
should move at once, and the corrections counter should stay at 0 while you walk; dropped frames show up as small,
smoothed corrections.

The scene is generated by `Editor/DevSceneBuilder.cs` (menu **MMORPG / Dev / Rebuild Prediction Dev Scene**); change
the builder instead of editing the scene by hand. Config comes from `data/tables` (`StartingValuesM1`,
`ClientPrediction`, `ClientCamera`), read with the same rules as the server.

The world (`WorldGeometryView`, **F3** (`Hotkeys` row `devWorldGeometry`) shows or hides it): at start it draws the exported world the server simulates
(`data/world/m1`, the files `ClientWorld` loads for prediction), so it cannot drift from the server. Brown walls are the
grid's blocked cells, which are exactly what collision and projectiles test: the blockers grown by the agent radius, so a
wall looks about 40 cm thicker than its box in the authoring scene. Yellow strips on the ground are the borders between
regions (city and combat area: the city wall and the gate) and the world's edge. The gray reference blocks only help
you see movement; the server does not know them. The builder keeps them off the walls, the borders and the spawn points.

## Dev tools (backlog J and A, spec 11.7)

Four tools for tuning (backlog K). The keys are the dev rows of `data/tables/Hotkeys.json`; F3 is the world view above.
They live on the scene's `Dev Tools` object (never part of the HUD), start hidden, and exist only in the editor and dev
builds. They read the local server's telemetry folder (`MMORPG_TELEMETRY_DIR`, else `<repo>/telemetry`), so the server
must run on this machine. Their settings are the `DevTools` table.

Start the server with its dev tools on: step 1 of "Run it" plus `$env:MMORPG_DEV_TOOLS = "1"` before `Start-Process`
(a Debug build: `dotnet run` builds Debug). The server prints `Dev tools on: tables in ... reload 300 ms after a change.`
Without it, the timeline and the tick panel still work, but the gizmos show only the client's shapes and nothing reloads.

- **F4, hitbox gizmos.** Lines on the ground, from the same `HitShapeDef` rows and frame the server tests:
  - **blue (predicted):** your strikes on their fire tick, and other players' and monsters' strikes from their
    snapshot state;
  - **orange (server):** the strikes the server really tested (its strike trace), exactly where and how it tested them,
    with every target circle it tested them against; **yellow** when the strike touched it;
  - **purple:** ground areas; **green:** projectiles (path so far and hit circle); **white:** every body circle (the
    radius the shapes are tested against).

  A shape stays for `gizmoHoldMs`. When blue and orange disagree, prediction (or the interpolated view of a remote
  entity) is not where the server is.
- **F5, action timeline.** Rows for your predicted action, the action the server acknowledged in its last snapshot of
  you, and your target: the last entity you hit or that hit you, else the nearest monster, at the render tick. Each row
  has phase bars in ticks (yellow startup, blue channel, red active, grey recovery), white marks on the effect fire
  ticks, and a black cursor at the current tick. Below them, strips of the last `timelineTicks` ticks of each row; a
  pink mark under a server sample means reconciliation found the predicted action different there.
- **F6, tick timing.** The server's own per-tick `TickTiming` telemetry over the last `tickWindowMs`: p50, p99, worst,
  ticks over the 50 ms budget, worst start lateness, overruns, and the last table reload on both sides. For a whole run
  offline: `dotnet run --project src/Tools/BotClient -- report --telemetry telemetry`.
- **Table hot reload.** With `MMORPG_DEV_TOOLS=1`, save a tuning table (for example `recoveryMs` of `attack.warrior` in
  `data/tables/ActionDef.json`) while you play.
  - **The server** waits until the files are quiet, runs every `DataValidator` check, and either swaps the tables in
    at its next tick (console: `Table reload accepted at tick N (ActionDef)`) or rejects the whole reload and lists
    every error (`Table reload REJECTED`); after a rejection it keeps running the old tables.
  - **The client** applies exactly the tables the server accepted (same file hash). F6 shows both sides; the console
    shows `[DevTools] applied the server's tables of tick N`.
  - **What you can change while playing:** values of actions, effects, hit shapes, projectiles, bindings, damage,
    ranks, elements, regen, classes, monsters, monster AI, statuses, status modifiers and build-ups.
  - **What needs a restart:** adding, removing or reordering actions, statuses, build-ups, monsters or classes;
    anything in start-up tables such as `StartingValuesM1`, `ServerLoop`, items, loot and spawn points. A reload that
    touches them is rejected.
  - **At the swap:** running actions end (like a cancel), cooldowns keep running clamped to the new cooldown, and
    statuses keep their time with their new values. Projectiles and ground areas already out finish as they were.
    New class and monster base stats apply from the next login or monster spawn.

## Visuals

Entities show the `EntityVisualDef` row of their visual id (`data/tables/EntityVisualDef.json`), loaded through
Addressables (in the editor straight from the AssetDatabase, no content build needed). The local player uses the
`Local Visual Id` of `EntityViews` (default `warrior`: also `archer`, `mage`, `assist`); other players and monsters use
the `visualId` of the `ClassDef` or `MonsterDef` row their spawn names, or the defaults next to it. A missing id or
prefab shows the capsule.

Monsters (backlog F): the server spawns the monster of each `SpawnPoints` marker of the sample world (two `m1.demon`, two
`m1.alien`). The nearest demon waits a few meters past the city gate (east of the spawn, 32 m away, just outside the
interest area): walk toward the gate and it appears. The monster AI (`MonsterDef`: `aggroRangeCm`, `leashRangeCm`, its
`attacks`) makes it come at you once you are within its aggro range and attack (the demon claws and pounces); past its
leash range, or when it loses you (it never follows you into the city), it walks home and heals to full. A monster that
dies respawns at its marker after `monsterRespawnMs` (30 s); a player who dies comes back at the city spawn after
`playerRespawnDelayMs` (5 s).

Keys of the fake action source (stand-in for D2's action machine, placeholder timings, not ActionDef values):
**1** attack (startup, active, recovery), **2** channel, **F** flinch, **G** stagger, **K** death, **L** back to
locomotion.

The prefabs, animation sets and Addressables entries under `Assets/Content/Visuals` are generated by
`Entities/Visuals/Editor/EntityVisualPrefabBuilder.cs` (menu **MMORPG / Visuals / Rebuild Visual Prefabs**, or batch
`-executeMethod Game.Gameplay.Entities.Visuals.Editor.EntityVisualPrefabBuilder.Build`). On a fresh Library the
VRM and glTF importers can fail once ("Parameter name: Shader": the model was imported before its shader), and Unity
keeps the failure; the characters then have no humanoid bones and hold no weapons. `FailedModelReimporter` (in the
builder's file) imports such a model again right after its import pass, and `EntityVisualTests` and the builder repair a
Library that kept the failure from before.

The builder also sets "Bake Into Pose" for root Y on every clip of the humanoid libraries (`BakeRootHeight`): the
animations play with root motion off (the entity root alone places the visual), and without the bake the hips lose their
bob and the feet float above the ground. Any replacement animation pack must either bake root Y into the pose itself or be
run through the builder (`LocomotionGroundingTests` fails otherwise); the walk and run reference speeds of each body are
measured on its avatar by the builder and scaled by `EntityVisualDef.scalePercent`.

Locomotion follows the movement relative to the facing (R-2.2-01: WASD moves, the mouse faces). `EntityView` measures
each entity's ground velocity from where it is drawn (predicted for the local player, interpolated for the others) in the
frame of its facing: along it and to its right (`GroundVelocity`, smoothed by `Speed Smoothing Ms` of `EntityViews`).
`VisualAnimationState` turns that into a blend of idle and eight directional loops (walk and run x forward, right,
backward, left; `LocomotionBlend.Directions`), and for bodies without side loops a leg turn (`LegTurn`): the hips turn
toward the movement and the spine turns back, so the chest keeps the facing (applied to the bones by `VisualAnimator`,
humanoids only). All of it is data in the `AnimationSet`: `walk` and `run` are the forward loops, the `walkBackward`,
`walkLeft`, ... slots hold the others (a clip, `reverse`, a reference speed the builder measures per direction), and
`legTurnMaxDeg`, `legTurnDegPerSec`, `legTurnHysteresisDeg` set the leg turn; `AnimationSet.LocomotionError` holds the
rules (checked for every set by `LocomotionGroundingTests`). While an action plays (the facing is locked, R-2.2-02) the
locomotion layer and the leg turn are faded out, so the dodge plays its own clip; afterwards they resume along the
movement of that moment.

PLACEHOLDER mapping (the Standard Quaternius packs have forward loops only): the four humanoids play `Walk_Loop` and
`Jog_Fwd_Loop` forward, the same loops in reverse when backing, and turn their legs up to 90 degrees for the sides
(hysteresis 15 degrees, 540 degrees/s). The monsters stay forward-only (one `Walk` take, generic rigs with no hips to
turn, and the monster AI always walks along its facing). A pack with real backward and side loops is a data change: the
builder fills the slots with them and sets `legTurnMaxDeg` to 0. The QA smoke step `footwork` strafes and backpedals in
view (`-strafe`, `-backpedal` shots).

The art under `Assets/ThirdParty` (and the LiteNetLib DLL) is in Git LFS. A new worktree can hold LFS pointer files
instead (Unity then stops with `CS0246 ... 'LiteNetLib'`, and the models fail to import): run `git lfs pull` (or
`git lfs checkout` when the objects are already in the local LFS cache) before the first Unity run.

## QA smoke run

`Qa/` holds a scripted run of this scene from the login screens (walk to the demon, kill it, Arrow Shot at a wall, wait
for the respawn, try the dev tools and a table hot reload) with a screenshot and a JSON result per step: `tools/qa/Run-QaSmoke.ps1`, see `tools/qa/README.md`.
