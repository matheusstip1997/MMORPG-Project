# Login screens (backlog B5, spec 9.10)

`Login/Login.unity`: title → server selection (one dev server) → character selection (slots, delete with
confirmation, enter world) → character creation placeholder (name + initial class). Enter world asks the Auth API for
the ticket and session key, connects with `ClientConnection`, and loads `LoginSettings.worldScene` (M1: the prediction
dev scene, which takes the connection from `Game.Net.WorldHandoff`).

- **UI Toolkit** (built-in module, no package): elements are built in code and placed from `data/tables/LoginLayout.json`
  in the 1280 x 720 reference space; the panel scales with the screen height (`LoginSettings`). Styles: `Login/Login.uss`.
- **Config**: `LoginSettings`, `LoginScreens`, `LoginLayout`, `ServerDirectory`, `ReasonCodeStrings`, `UiStrings`, plus
  `CharacterCreationConfig` and `NetSecurity`. No user-facing text in code: labels come from `UiStrings`
  (`Config/UiTextIds.cs`), refusals from `ReasonCodeStrings` (every reason enum is checked by the DataValidator).
- **Structure**: `Auth/` (Auth API client over `IAuthHttp`, login ticket sources), `ViewModels/` (state only, `Changed`
  events), `Presenters/` (one per screen, redraw on `Changed`), `Login/LoginFlow.cs` (navigation and calls),
  `Login/LoginRoot.cs` (scene entry point).
- **Dev login**: in the editor and in builds with the `MMORPG_DEV_LOGIN` scripting define the client signs in with
  `dev:<n>` (`LoginRoot.devSteamId`, or `-devLogin <n>` on the command line). Otherwise it uses the Steam ticket source,
  a stub that reports `SteamUnavailable` until Steamworks is integrated.
- **HTTPS**: the client only calls `https://` or loopback `http://` (`AuthEndpoint`); "Allow downloads over HTTP" is set
  to development builds only. Production uses an `https://` `authApiUrl` with TLS in front of the Auth API (TODO(infra)).

The scene is generated by `Login/Editor/LoginSceneBuilder.cs` (menu **MMORPG / UI / Rebuild Login Scene**; it also
puts the login and world scenes in the build settings). Edit the builder, not the scene.

# HUD v1 (backlog I, spec 9.12)

The main HUD in the world scene (M1: the prediction dev scene). Same approach as the login screens: UI Toolkit built in
code, one view model per element, presenters that redraw on `Changed`, layout, theme and text from tables.

- **Config**: `HudLayout` (one row per spec 9.3 element; hotbar `slots` by `ActionBindings` skill slot), `HudSettings`
  (reference resolution, timings, pool sizes, boss engagement timeout), `HudThemeTokens` (colors and font sizes, spec 9.7),
  `UiStrings` (`hud.*` ids in `Config/HudTextIds.cs`; names `action.<id>`, `monster.<id>`, `rank.<Rank>`,
  `status.<id>`, checked by the DataValidator), `ReasonCodeStrings` (the refusal toast). `Config/HudConfig.cs` wraps them.
- **Data path**: the world client (`PredictionDevClient`) raises a `WorldClientFeed` (`Game.Gameplay.Entities`);
  `HUD/HudFeedBinder.cs` is the only HUD class that reads it, the registry and the predictor, and fills
  `ViewModels/Hud/`. Cooldowns, recharge fills and the cast bar animate from stored end times.
- **Structure**: `HUD/HudRoot.cs` (scene entry point, scaling, wiring), `HUD/HudPresenters.cs` (resource panel, hotbar,
  locked class gauge, parry/dodge squares, buff row, boss bar, cast bar, toast, chat frame), `Overlays/` (name plates and
  monster HP bars, damage numbers, telegraphs: ground meshes from `HitShapeDef` plus a color icon), `HUD/Hud.uss`
  (structure only; colors come from the tokens). Font: Barlow Semi Condensed (`Assets/ThirdParty/Fonts`, OFL).
- **Scene**: `HUD/Editor/HudSceneInstaller.cs` adds the HUD object (UIDocument, `HudPanelSettings.asset`, `HudRoot` with
  styles, font, telegraph shader and the client) when `DevSceneBuilder` rebuilds the dev scene.
- **Tests**: `Tests/Editor/HudViewModelTests.cs`, `Tests/Editor/HudLayoutAndPresenterTests.cs` (every row against the
  spec 9.3 positions, presenters, theme, telegraph meshes, the dev scene's HUD links). The QA smoke checks the resource
  panel, damage numbers, the demon's plate and HP bar.
- **Not yet**: local chat (follow-up; the panel is a frame), party frame, minimap, region header, run tracker, exp bar,
  shortcut row, build-up meters, HUD modes, hotbar and buff icons.

## Try it locally

**One command** (spec 11.3): at the repository root, with Docker Desktop running,

```powershell
docker compose up -d --wait
```

starts PostgreSQL, Redis, the migrations, the Auth API with the dev login on `http://127.0.0.1:5080`, the GameServer on
UDP 7777 and the admin panel on `http://127.0.0.1:5090` (`src/AdminPanel/README.md`), with dev secrets generated once.
Then press Play in the login scene as below. After a server change, rebuild with `docker compose up -d --wait --build`;
a table edit in `data/` needs only `docker compose restart gameserver authapi`. Logs: `docker compose logs -f gameserver`.
Stop with `docker compose stop` (`docker compose down -v` also deletes the dev databases and secrets).

**By hand** (to debug a server from the IDE): start only the databases, and stop the composed servers first if they
are running (`docker compose stop authapi gameserver adminpanel`), since they hold ports 5080 and 7777. In PowerShell
at the repository root:

```powershell
docker compose up -d --wait postgres redis
dotnet run --project src/Tools/DbMigrate -- --dev

# Same ticket secret for the Auth API (issues tickets) and the GameServer (checks them).
$env:MMORPG_TICKET_SECRET = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
$env:MMORPG_TICKET_KEY_ID = "1"; $env:MMORPG_REALM_ID = "1"; $env:MMORPG_GAME_PORT = "7777"
$env:MMORPG_GLOBAL_DB = "Host=127.0.0.1;Port=5432;Username=mmorpg;Password=mmorpg_dev;Database=mmorpg_global"
$env:MMORPG_REALM_DB = "Host=127.0.0.1;Port=5432;Username=mmorpg;Password=mmorpg_dev;Database=mmorpg_realm_1"
$env:MMORPG_REDIS = "127.0.0.1:6379"
$server = Start-Process dotnet -ArgumentList 'run --project src/GameServer' -NoNewWindow -PassThru

$env:MMORPG_AUTH_TOKEN_SECRET = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
$env:MMORPG_AUTH_IDENTITY = "dev"
$auth = Start-Process dotnet -ArgumentList 'run --project src/AuthApi' -NoNewWindow -PassThru
```

Then open `Assets/Game/UI/Login/Login.unity` and press Play: any key on the title, **Enter server**, **Create new
character** (name of 3-16 ASCII letters), **Enter world**. Stop the servers started by hand with
`Stop-Process $server.Id, $auth.Id`.

Things to check: stop the Auth API and press a key on the title (`AuthApiUnreachable`); create the same name twice
(`NameTaken`); create five characters (`NoFreeSlot`); delete one (the card shows the days left); stop the GameServer
and enter world (`ConnectionTimeout` or `GameServerUnreachable`).

## End-to-end test

`Tests/Editor/LoginEndToEndTests` runs the same path headless (login, create, list, enter, game connection accepted)
when `MMORPG_E2E_AUTH_URL` is set, with both servers running as above (the composed stack or by hand):

```powershell
$env:MMORPG_E2E_AUTH_URL = "http://127.0.0.1:5080"
& "C:\Program Files\Unity\Hub\Editor\6000.3.26f1\Editor\Unity.exe" -batchmode -projectPath unity -runTests -testPlatform EditMode -testFilter LoginEndToEndTests -testResults e2e.xml -logFile -
```
